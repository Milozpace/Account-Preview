# 版本与分支管理

> 2026-11-07 修正：个人开发版与公开发布版分别管理产品版本和交付分支。个人构建以本机个人版本配置为准，公开版本以 `release.json` 为准；用源码提交、源码版本和组件哈希记录关联。下文统一产品版本的表述为历史约定，不作为本轮交付规则。

2026-11-06 起执行。维护者要求将版本管理讨论中的分支、渠道、标签和共享核心原则纳入项目规范，并确认同一源码产品版本共用编号。本文取代旧的“personal 长期使用独立 0.3.x 产品版本线”约定；既有版本和安装回执保留作历史，不改写。

## 先分清六种信息

| 信息 | 回答的问题 | 依据 |
|---|---|---|
| 产品版本 | 这次交付包含哪些功能和兼容性 | `release.json`，例如 `0.4.0-preview.5` |
| 发布渠道 | 以什么稳定程度、节奏提供给谁 | 开发候选、公开预览、未来稳定渠道；与安装身份分开 |
| 安装身份 profile | 包装到哪个应用及其数据/配对空间 | preview / personal，保留包 ID、签名、配置目录和云命名空间 |
| Git 分支 | 哪条代码线正在继续演进 | main / dev / feature / fix / hotfix / release |
| 提交和构建标识 | 精确用了哪份源码和哪些组件 | 完整 commit、构建记录、平台及组件哈希 |
| 设备安装状态 | 某设备实际装了什么 | 部署回执与实际应用核对，不能由源码清单推断 |

personal 可提前使用较新开发候选，朋友继续使用较早已发布预览。同一源码版本构建的两种身份共用产品版本，不要求同时交付。身份表示安装隔离，不是功能等级或永久私人代码分叉；实验性偏好优先用配置/功能开关管理，开关不能绕过数据、权限、契约和发布校验。

原生 `nativeVersion` 和 Android `versionCode` 负责覆盖安装顺序，由工具维护并严格递增，不作为另一套用户产品版本。Web/App `schemaVersion` 表示快照兼容；云端 revision 表示该用户展示数据的修订；业务 sourceHash 表示账本内容及计算版本。它们都不能代替产品版本或源码 commit。

## 分支职责与合并方向

| 分支 | 从哪里开始 | 职责与合入方向 |
|---|---|---|
| `main` | 已验证的交付基线 | 接收已完成发布验收的代码；未来稳定线。当前仅有公开预览，不因此宣称已有 Stable |
| `dev` | 当前已验证基线，迁移时保留已提交开发成果 | 集成下一轮功能；可产开发候选，不直接等同可公开交付 |
| `feature/<事项>` | dev | 短期功能、规范或开发支持改动，验证后合回 dev |
| `fix/<事项>` | dev | 开发线问题修复，验证后合回 dev |
| `release/<主.次>` | 拟发布的 dev 固定提交；旧版维护则从相应已发布 tag | 按需冻结候选或维护旧版；收敛后合入 main，相关修复回流 dev |
| `hotfix/<事项>` | 受影响的已发布 tag 或对应 release 线 | 只修旧版问题，进入对应维护线/main，并移植到 dev |

原有 `codex/*` 分支保留，不批量改名、删除或强推；需要继续其中任务时先核对来源和未合入提交，再按上述职责衔接。新任务使用有具体事项的短期分支，不长期把某个 feature 当 dev；本地自动化仍可用等价的 `codex/<事项>` 名称，必须记录目标基线和合入方向。

开发开始先核对工作区、当前分支、main/dev 与远端关系；保护已有修改。需要隔离时使用独立工作副本，不在使用者账本目录开发，不通过 reset/clean 清现场。合并前看差异、解决冲突并验证，不能把“没有冲突”当成逻辑正确。

功能先经短期分支验证合入 dev；准备交付时选定完整 commit，冻结后专注修复与兼容。整批功能都达到交付标准才把对应代码推进 main；若只需稳定线小修，从已发布基线选择性移植，不能把 dev 未完成功能一并带给用户。使用 `cherry-pick` 时记录原提交与新提交、解决语义冲突并重跑回归；完成后让修复回到 dev，避免下一版复发。

分支存在不等于授权推送、合并到 main 或发布。按本次授权执行可逆本地分支管理及提交；远端与发布仍按[开发同步与发布规范](开发同步与发布规范.md)的边界。

## 什么时候编号

普通源码提交、实验和仅文档修订用 commit SHA 区分，不每改一行就升产品版本、不为每次提交建发布 tag。准备真正交付的候选（包括要交给他人覆盖安装的包）时才确定产品版本；候选未批准前报告“未发布 + 完整 commit + 构建标识”。源码保留上次 release.json 不代表新提交仍是那个已发布版本。

本地覆盖安装（USB 直装、本机验收）只看效果，不等于交付，也不消耗版本号：同一目标版本可以有多个本地构建，共用 `release.json` 的产品版本、原生版本与 Android code，靠完整 commit、构建时间和组件哈希区分，按 `p5-dev-<短SHA>-<日期>` 一类构建标识记录，不写回 `release.json`。测试期不要为每次构建递增原生版本或 code——递增过的号会让将来真正发布的较低序号无法覆盖安装；确需同号或降级覆盖时，只在本地测试设备使用 `adb install -r -d` 并在回执写明原因。版本号只在真正分发或发布时定稿，定稿后按下表冻结。

| 变更 | 编号原则 |
|---|---|
| 向下兼容修复 | 递增 patch |
| 向下兼容新增功能 | 递增 minor，patch 归零 |
| 已定义公共契约不兼容 | 1.0 后递增 major；0.x 预览期明确迁移及兼容窗口，产品系列是否调整由维护者确认，不按 schema 自动跳 minor |
| 同一目标版本的预发布交付 | 使用并递增 alpha.N / beta.N / rc.N，或继续已有 preview.N 系列 |

项目采用 [SemVer 2.0.0](https://semver.org/lang/zh-CN/spec/v2.0.0.html) 的版本排序与发布不可变原则；0.x 不承诺稳定公共契约。快照 schema 升级不机械等于产品 major 升级，但必须评估旧客户端、缓存和更新器兼容。示例 `1.5.0-alpha.1 < 1.5.0-beta.1 < 1.5.0-rc.1 < 1.5.0` 不是实际发布记录。

维护者 2026-11-06 确认本轮继续 `0.4.0-preview.4 → 0.4.0-preview.5`，收入及 App schema 3 随 preview.5 候选交付。已有预览系列内的迭代可递增 preview 序号；Agent 应先提出具体版本建议并取得维护者确认，再改变产品系列，不能把功能新增或内部 schema 变化当作自动升到 0.5.0 的授权。此前未交付的 0.5.0 草稿不构成已安装升级下限；已发布或实际交付的版本仍不可重用、降级或改写。

某个预览或实验不必最终发布；正式版本也不必追上每次开发更新。构建元信息或 commit 不能用来绕过同一发布版本不可替换、安装序号不可倒退的约束。实际已分发候选有变化时分配新交付编号，不重用已有版本覆盖其资产。

## 版本工具和交付事实

共享版本输入是 `release.json`，npm/Cargo/Tauri/Android 版本由 `scripts/product_version.py` 生成，禁止手工逐处修改。personal 默认读取同一产品/原生版本与安装序号；旧 `local/personal-version.json` 仅作为历史兼容与升级下限，不再决定新产品版本。个人构建继续在不含账本的隔离源码副本中选择 profile，个人组件仍只保存在本地。

```text
PY scripts/product_version.py check
PY scripts/product_version.py set --version 计划交付版本
PY scripts/product_version.py set --version 计划交付版本 --apply
PY scripts/release.py version-check
```

先 dry-run，再核对所有已交付的原生版本/code 下限，正式修改后验证生成文件；产品版本增加不能使安装号降级。构建、bundle、prepare 和更新预检必须一致绑定产品版本、完整 commit、平台、profile、原生版本/code。旧 personal-local 索引按原格式校验保留恢复能力；新统一索引不能伪装成旧格式绕过一致性保护。

远端更新目前继续订阅兼容的 `X.Y.Z-preview.N` 发布标签与历史 `private-preview` 协议频道；这不是仓库私有性或安装身份。支持生成 stable/alpha/beta/rc 版本不等于已实现对应远端订阅，首次交付这些渠道前另验收更新发现、比较、索引和旧客户端行为。不要直接改 wire channel、给所有用户切频道或把不同身份包混装。

发布目标看 release.json，公开事实看远端 tag/Release 与固定资产，设备事实看各自安装回执。开发状态表只作带时间和来源的索引，不手工维护第二套事实。默认分支 HEAD、dist 文件名或某个安装配置都不能单独证明“最新版已安装”。

## Tag 与 Release

实际交付固定版本和完整 commit。公开交付获准后用 `v<产品版本>` tag 固定，经批准的 Release 对应相同 commit、说明和资产。优先创建附注标签；历史已发布标签保持原样，不能为统一风格重写。更新本地缺失 tag 用 fetch，不重新制造或移动远端标签。

本地 personal/开发候选在交付回执固定版本、commit 和组件哈希，可先于公开 tag/Release；这不代表公开发布。没有给个人包创建公开标签的默认授权。已公开版本的 tag、包、说明和校验值不原地替换；修正另发新版本。

CI 只验证并产候选，不自动升号、建 tag 或发布。先由 Agent 起草发布说明，维护者润色或确认最终稿及该版本发布；按白名单上传公开资产，personal 和本机草案不混入。

## 新开发者的固定操作清单

开始：读 `AGENTS.md` → [开发状态与交接](开发状态与交接.md) → 本文 → 涉及的架构/契约；确认源码根、基线、目标分支、版本状态和本次授权，按需读本机 `local/开发环境.md`。共享开发不依赖作者个人仓或某个 agent 专属记忆。

完成：相关回归和兼容验证 → 更新受影响契约及共享交接状态 → 精确暂存本次文件并提交 → 按授权合入目标开发线。草案留忽略的 local 目录，稳定通用规范随代码入库；不夹带个人数据或其他未完成任务。

交接至少写清：功能/问题、分支与目标、来源 commit、产品版本及是否已分配、候选/公开状态、已执行测试、未验收设备、实际部署回执位置和下一步。状态相关值写核对时间，不把旧值复制成当前事实。示例报告模板：

```text
源码：分支 / 完整 commit；目标合入 dev 或指定维护线
版本：产品版本或未编号；开发候选 / 公开预览 / 稳定
身份与构建：profile / 平台 / nativeVersion / versionCode / 组件哈希
验证：实际通过、失败、未执行；兼容范围与已知限制
交付：已提交、已合入、已构建、已安装端、已发布分别列出
续接：共享状态入口、相关契约及本机证据位置
```
