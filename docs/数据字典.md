# 数据与审核契约

本页用于核对存储结构与审核格式，日常执行从[记账 Skill](../.agents/skills/account-maintenance/SKILL.md)开始。业务定义见[记账规则](记账规则.md)，快照兼容见[快照与月份](快照与月份.md)。Schema 以 `scripts/ledger_store.py` 为准，字段白名单以 `scripts/account.py` 的 `HEADERS` 为准。

## 存储与单位

| 表 | 内容/约束 |
|---|---|
| `metadata` | schema/revision 元信息；新初始化账本另存 `budget_mode=zero-observation-v1` 与对应 calculation_version |
| `ledger` | 身份、序号、唯一键、父/关联 ID、整数分和业务 JSON |
| `budget_rates` | 生效月和四池额度；常规追加，显式修订须预检、备份和审计 |
| `initial_carry` | 初始滚存，运行/随心为零 |
| `import_batches` | 来源、审核、增改数、修订、前后哈希 |
| `audit_log` | 前后值、原因、确认来源、审核/写入时间，不可覆盖 |

金额用整数分，审核 JSON 可用十进制元文本，空值不补零。订单和关联 ID 为文本。`sourceHash` 是规范化业务、预算、滚存及计算版本的 SHA-256，不是数据库字节哈希；新初始化账本的 `budgetMode=zero-observation-v1` 也纳入业务哈希。已有未标记账本保持原计算及原哈希，不因程序更新自动加标记；备份不改业务版本。

当前 App schema 3 使用 `coverage.kind=tracked-months`，按本人账本起点连续保留历史。同一受支持 schema 内的旧 `recent-months` 仍按精确两月校验，schema 兼容另行核对。更新清单的 commit、版本和组件哈希标识程序来源，账本 sourceHash 单独描述业务内容。

可选 `local/display.json` 的唯一字段 `trackingStartMonth` 是本人确认的展示起点，不是预算生效月，不改变流水或业务 sourceHash；缓存与导出须另核对该配置对应范围，不能仅凭同一 sourceHash 判断展示最新。配置只在本人本机维护，采用旧个人版时保留其明确设置。

当前 init 的 amounts 可省略，默认写完整四池零额度和零初始滚存，仅新初始化账本写入观察模式。该模式下首次正数生效额度之前的月份 `mechanismActive=false`，真实分池消费可见，超支、滚存欠账和安全积累按观察模式处理。明确非零初始滚存按机制已启用处理，首次正数额度之后的零额度月份继续正常机制。当前 SQLite schema 为 1，Web 为 2，App 为 3；mechanismActive 表示该月预算机制是否启用，UI 观察期显示“未设预算”。

已有未标记账本保留原计算，不能从既有零值猜意图或自动迁移。首次审核必须按用途证据完成主分类和分池；真实歧义可解释后待定，并分别报告覆盖笔数、金额及原因。不能因预算未制定整批留待归类。默认零预算不适用于任何缺失交易金额。

## 计算模式与审核覆盖

新初始化在 metadata 写入 `budget_mode=zero-observation-v1` 以及独立的 `calculation_version=sqlite-ledger-calculation-v1-zero-observation-v1`；模式纳入业务 sourceHash。旧版工具不认识新计算标识时会拒绝读取，不会静默套用旧算法。未标记的已有账本继续使用原计算标识和哈希，不自动迁移。

import 的 `classificationReview` 仅统计本批实际新增/修改的非零本人/项目消费，包含消费总笔数、已分池/待分池笔数、待分池净额、缺少主分类笔数及警告；`reviewComplete` 仅本批所有此类记录均有主分类和池时为 true，不是整库状态或入账成功标志。真实待确认可以保留并说明具体原因；此时为 false，不能称全部分类完成，也不为清警告猜测。重复预检无变更时该批计数为零，不代表整库已经完成分池。

## 36 个持久字段

| 分组 | 字段 |
|---|---|
| 原始事实（不可按分类改写） | 平台、交易时间、交易对方、商品/说明、原始类型、原始分类、收支方向、原始金额、支付方式、状态、交易订单号、商家订单号 |
| 事件/金额 | 原始财务事件、退款调整、净支出候选、最终财务事件、统计口径、计入消费金额 |
| 分类/解释 | 主分类、细分类、生活领域、服务对象/事件、标签、语义置信度、语义说明、用户修正规则、复核状态 |
| 资金池 | 资金池、资金池判定 |
| 追溯 | 来源行、记录ID、原记录ID、关联记录ID、来源文件、导入批次、记录类型 |

月份/排名由程序派生，不持久存入业务字段。`tx_` 为原交易身份，`alloc_` 派生行须关联原行并校验金额。未知分类留 Unknown/待归类，不虚构置信度。

## 审核 JSON

由 prepare 生成，避免手写原始行或伪造出处。Agent 补 `reviewed_by`、`reviewed_at` 和实际依据，`review_required` 不等于已审定。来源清单含原文件路径与 SHA-256。日常操作必读 [Skill](../.agents/skills/account-maintenance/SKILL.md) 及其审核契约；不必为每批通读本字典。

当前 CLI 对新增记录要求 prepare 的 `source_files`；声明来源时工具重新核对文件哈希、解析原件并绑定原始字段/来源位置，阻止手工重构或错配来源。旧库无清单的历史批次保留兼容，不据此给新批省略来源。整批验证行、更新和来源，失败回滚；部分暂缓后用原归档重新 prepare，保留新输出生成事实。

首次审核也沿用 prepare 输出的整个 JSON，在其中补充如下信息，不另建缺少来源的简化文件：

| 位置 | Agent 应填写或保留 |
|---|---|
| `reviewed_by` | 当前实际 Agent/审定者标识；不得为空，不需要搜索旧审核者姓名 |
| `reviewed_at` | 本次审定时间，使用带时区的 ISO 8601 文本 |
| `reason`、`confirmation_source` | 实际判定理由和证据/用户确认出处；不能编造用户确认 |
| `source_files` | 完整保留 prepare 记录的路径和 SHA-256，不改原件或伪造哈希 |
| `records` 每个新增行 | 明确提供 `最终财务事件`、`统计口径`、`计入消费金额`、`主分类`、`资金池`、`语义说明`；结合规则填写其余派生字段，保留原始 12 字段和 ID |
| `conflicts` | 非空时先定位、解决冲突，不能把冲突改称重复或直接覆盖 |
| `review_required` | 完成实际审核后可标为 false；单改此标志不构成审定，也不授权长期规则 |

先执行不带 `--apply` 的 import，依据准确错误补齐审核，预检通过且本批已获记账授权再执行写入；不得为绕过校验修改原始事实。

## 审核字段取值

SQLite 计算以 `scripts/ledger_calculation.py`、导入校验以 `scripts/ledger_store.py` 为准。不要沿用旧 Excel 汇总器较宽松的中文别名。

| 字段 | 当前约束与建议 |
|---|---|
| `统计口径` | `计入消费金额` 非零（含负数退款）时只能用 `PERSONAL`、`PROJECT` 或 `STRUCTURAL`。PERSONAL/PROJECT 参与本人净消费与分池，STRUCTURAL 单独统计、不进四池。规范填写大写英文，不能写“个人消费”等中文别名。 |
| `INCOME` 收入口径 | 经审核确认的实际收入。金额就是实际到账的 `原始金额`，`计入消费金额` 必须为 0，`资金池` 必须为空，`主分类` 必填（自由文本）。收入独立于消费、四池与滚存计算。互转、报销返还、代收代付、借款不是收入。负向收入必须用事件 `income_reversal`，金额严格小于零，`关联记录ID` 必须指向原始正向 INCOME，不能指向消费、另一冲回或分摊。`退款调整` 不允许非零值。收入聚合由 `ledger_calculation.income_aggregate` 计算；`inspect` 月度 `incomeCents` 为整数分，`incomeCount` 为整数笔数。 |
| 零金额的口径 | 当前零值没有强制封闭枚举，但仍须提供字段；确认不计消费规范使用 `EXCLUDED` 并写排除依据，不输入旧 Excel 中文口径或“不计入”等旧别名。确实已知为零而语义待核对才可 `UNKNOWN`；金额/净额未知留候选，绝不补零。 |
| `最终财务事件` | 当前不是强制封闭枚举，按证据写可解释文本，如 `purchase`、`refund`、`transfer`、`reimbursement`；事件名称不能代替合法统计口径。 |
| `主分类` | 用户可理解的自由文本，未强制固定分类体系；不确定保留 Unknown 并解释。 |
| `资金池` | 空值、`运行账户`、`随心消费`、`旅行/体验`、`成长/项目/耐用品` 或 `待归类`。安全积累是计算结果，不是第五个池。 |
| `记录类型` | 普通行建议 `原始交易`；派生分摊建议 `派生分摊`，工具还识别大小写精确的 `分摊`、`派生`、`allocation`、`DERIVED`。须关联非派生原行、满足金额平衡和身份约束，不靠改名称规避分摊校验。 |

原始金额、方向和来源证据不可为表达冲回而修改。第一版冲回仅接受原始来源本来就是负金额的审核记录；若原始账单以正金额支出表达追回，不能把原始金额改负、冒充退款或普通正收入；保留原件并暂缓该收入冲回分类，明确需补审核表示法/独立设计。普通消费退款继续按原支出规则处理。`inspect` 中历史消费聚合的元字符串与新 `incomeCents` 的整数分命名要区分，不对整数分重复换算。

以下仅为 prepare 生成的某条记录中**派生审核字段片段**，使用虚构金额；不是可独立导入的 JSON，不替换原始字段、来源或 ID：

```json
{
  "最终财务事件": "purchase",
  "统计口径": "PERSONAL",
  "计入消费金额": "12.34",
  "主分类": "日常餐饮",
  "资金池": "运行账户",
  "语义说明": "虚构示例：已说明为本人工作日普通午餐，用于日常生活；按用途分入运行账户"
}
```

ID 由 prepare/规范化流程生成，不手编；派生行必须使用 `alloc_` 并关联已有的非派生原行。附真实审核理由和确认来源，单笔确认仅作用该笔。预算的生效月继承与历史修订见[四池预算设置](四池预算设置.md)。

`records` 为候选新增，`updates` 显式改白名单派生字段，每项含 `记录ID`、`changes`、`reason`、`confirmation_source`。原始前 12 字段、`记录ID`、`来源文件`、`来源行` 不可更新，不能在同批 updates 中绕过原件定位检查；规则不得自动覆盖旧确认。冲突须解决，不算成功重复。

快照白名单脱敏，使用整数分与版本；未经契约变更不把订单、账号或完整出处加入展示。

## 展示与回执口径

当前 `INCOME` 进入独立 incomeRecords 与收入汇总，消费明细按消费口径展示。EXCLUDED 的互转等记录保留在 SQLite。核对丢单问题时先确认所属口径及该展示的范围。

手机回执 `pending` 表示来源仍有未入账候选；`blocked` 表示来源变动、冲突、缺失或证据错误等阻塞，令回执结果 `ok=false`。`receiptErrors` 单列上传失败。均需与 SQLite 批次和审计核对，续接见[记账 Skill 恢复说明](../.agents/skills/account-maintenance/references/recovery.md)。
