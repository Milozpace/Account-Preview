# 让 Agent 逐渐了解你的记账方式

首轮 mini 先体验 Agent 整理账单和电脑可视化，不必在开始前设计所有预算、分类和私人规则。先用通用证据原则，逐步完善本机档案与 `local/个人规则.md`。每个人的预算、分类和生活场景独立，当前试用版不承诺完整个性化支出管理。

## 先区分用户这次表达的意思

| 用户表达 | 记录或操作 | 生效范围 |
| --- | --- | --- |
| “想看看餐饮花了多少” | 本机档案记录关注点 | 本次分析或后续观察 |
| “这笔是通勤”并要求纠正 | 按 Skill 定位原 ID、审计 updates | 本次指定记录 |
| “满足这些条件时以后都这样” | 核对条件、例外与批准出处，写个人规则 | 明确批准的范围 |
| “从某月改这个额度” | 按四池预算文档预检和保存 | 指定生效月及其继承区间 |

记住偏好依靠本机文件和实际重读。新会话从档案与批准记录续接，检查当前证据是否满足规则条件。

## 从一月记录开始，再做简短访谈

本人选择近期一个月的本地文件，Agent 按 [日常记账 Skill](../.agents/skills/account-maintenance/SKILL.md) 批量解析、审核和核验。用途明确的消费完成主分类与四池，不等预算或访谈；影响真实净额的转账、退款、报销疑点先问。少量小额且真实用途不明可保留实际金额，写具体待定原因并在完成后简短报告，无需逐笔盘问，也不为覆盖率猜测。首批不要求每笔都形成永久规则。

电脑上看到实际结果后，先问两个问题，必要时再问第三个：

1. “这一月有哪块支出出乎你的意料，或是接下来想留意的？”
2. “这些分类有没有不贴近你习惯的，想合并、拆开或改名的？”
3. 需要进一步了解时：“想先继续观察，还是给某一块支出记一个目标？”

允许回答“不确定，先记着”。一月样本和当前文件覆盖不足以推断长期合理额度、消费习惯或适合所有人的分类；Agent 不直接给用户贴超支/不自律标签。

本人确认的关注点先记本机 `local/档案.md`，区分“想关注”“建议候选”和“已经批准”。关注意向不是正式金额上限，不自动写入预算、改历史或推广长期商户规则。分类只做少量有依据的修正，历史批量改类另明确范围。

预算未制定时按开始使用的零技术占位解释，暂不解读预算区。以后本人明确想做预算管理，再说明当前四池的固定结构是否适合，确认额度和后续生效月；不适合或暂不想定时继续观察即可。日常主分类可以渐进调整，改文字不等于程序已支持自定义资金池模型。

## 单笔确认与长期规则

“这笔是交通”只确认该笔，不等于“这个商家以后都算交通”。Agent 记出处、保护该笔；后续证据不足仍留 Unknown。

金额影响大、影响多月/多个池、退款/报销关系不清，或真实规则冲突时主动澄清。反复出现且影响结果的用途歧义可集中澄清；少量低影响项目可明确 Unknown 并解释，不强制每笔询问。不能为少问而猜，也不反复问已有批准规则明确覆盖的场景。用户已明确纠正并要求修改的记录，直接按 Skill 的显式 updates 核验闭环，无需第二次入账批准。

`PROJECT_MEMORY.md`、旧审核文件和 Agent 生成的历史笔记只能作为待核对线索；没有本人批准出处，不能视为已生效个人规则。单笔确认也不能冒充长期批准，不能引入作者或其他用户的商户经验。

## 推广流程

1. 提候选：触发条件、证据字段、事件/分类/池和复用理由。
2. 列例外、排除条件、生效范围及是否仅未来；金额匹配不能单独作依据。
3. 取得用户**同意建立长期规则**的明确回复。单笔回复、未回复、“先记这笔”不算批准。
4. 写入本机个人规则，记 ID、批准日期、出处、版本，执行时引用规则 ID。
5. 条件不足/冲突/例外时 Unknown 并询问。已有确认保持；重判历史另列范围、获授权并审核更新。

用[个人规则模板](../templates/个人规则.md)，候选与生效规则分开，候选不自动执行。

## 新会话与版本更新后

读取本人已有档案和个人规则的相关部分，保留批准日期、范围和例外。程序更新后的日常执行入口按[更新与恢复](更新与恢复.md)核对。遇到旧笔记与本人明确确认不一致时，先核查出处；范围清楚的既有批准继续执行，真正的业务歧义再问。

## 完全虚构的演练

用户确认一笔“演示交通服务”为通勤，只修该笔。下一笔同额不能照搬。若另批准“仅用途明确为通勤车票且非退款/代垫时归运行账户”，才记长期规则。用途不清或与旧确认冲突仍复核；此例无真实商家、金额或默认额度。
