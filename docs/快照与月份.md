# 快照月份与升级兼容

本页供 Agent 处理跨版本展示与开发者检查契约。SQLite 是唯一账本，网页和 App 读取统一计算的派生快照。schema、产品版本与云端 revision 分别核对。

## 版本与展示范围

| 版本 | Web schema | App schema | 需要核对什么 |
| --- | --- | --- | --- |
| preview.4 | 1 | 2 | 使用该版原有收支口径 |
| preview.5、rc.1 | 2 | 3 | 支持独立收入明细与汇总，升级旧端时协调组件 |
| 后续交付 | 以固定源码和索引为准 | 以固定源码和索引为准 | 同时核对生产端与消费端 |

加密、身份和双槽沿用原协议。收入历史复核见[版本衔接指引](版本衔接指引.md)，执行更新见[更新与恢复](更新与恢复.md)。

App 3 的月视图增加 incomeRecords、incomeCategories，summary 增加整数分 incomeCents。INCOME 明细与消费、日历、资金池及预算独立，分类名称集合、逐类金额/笔数和汇总必须与明细完全一致，包括净额为零的分类。仅已审核入账收入进入快照；没有收入导入不等于现实中没有收入。

新导出 App coverage.kind 为 `tracked-months`。SQLite 导出起点取本人最早预算生效月、本人最早交易月与当前月的最小值，从当前月连续降序导出到起点，包含没有交易的空月。未来翻月只增加月份，不滚动删掉历史；新用户不会继承作者的九月起点。未来生效参数的空库至少展示当前月，不虚构旧月份。

本人已经确认展示起点时，使用忽略的 `local/display.json`，格式仅为 `{"trackingStartMonth":"YYYY-MM"}`。它优先于自动推导，不删除较早交易或改变预算；未来起点至少显示当前月。个人原版采用时只读解析本人的旧 `TRACKING_START_MONTH` 明确常量并保存在该文件，不执行旧代码、不把它发给其他用户、不重置程序基线；已有本地设置优先保留。配置不合法或路径重定向会停止导出并保留有效快照。展示设置不改变业务 sourceHash，因此网页与 App 另行比较范围，配置变化后旧范围不能标为最新。

Python 与原生校验器要求 coverage.months 与实际 months 完全相符、首月为 calendarMonth、日期合法、无跳月或重复，并继续核对各月净额、分类、四池和明细。接收快照的客户端无法仅凭连续月份证明最早月是否为该用户实际起点；这一点由持有 SQLite 的导出端核对。

同一支持 schema 内，`recent-months` coverage 继续严格接受本月和上月两个月；`tracked-months` 接受连续历史。coverage 和 schema 分别检查。preview.1 使用两月范围，preview.2 起支持本人连续历史；收入在 preview.5 起交付。源码、App 和 helpers 使用匹配版本。

## 收入升级兼容矩阵

本轮选择严格拒绝不支持的 schema，保留原缓存文件，不把旧快照缺少的收入字段补零冒充已核验收入。旧缓存内容不能被当成当前契约的有效数据；新快照生成/认证成功前不删除或覆盖最后有效文件。

| 组合 | 预期与恢复 |
|---|---|
| 新导出器 + 旧 app/helper | 旧原生校验拒绝 App 3；先交付同提交 app 与三件 helpers，再本地刷新 |
| 新桌面 + 旧本地 App 2 | 明确提示契约升级，原文件不变；从本人 SQLite 本地重建 App 3，不重新导入交易 |
| 新手机 + 旧云端 App 2 | 拒绝并保留云端/本地原件；待同版电脑生成并按已有授权发布 App 3，再刷新 |
| 旧手机 + 新云端 App 3 | 旧端拒绝未知契约并保留其原有效缓存；覆盖安装同版手机后读取，不清数据/重配对 |
| 新端 + 新 App 3，本地离线 | 已认证 App 3 缓存可读，云端状态不冒充最新；无有效 App 3 则明确尚不可用 |
| 新端遇到坏快照/分类不完整 | 验证失败不覆盖有效缓存；定位生成或传输问题，不手改快照金额 |

## 升级操作顺序

固定交付提交与兼容说明 → 同轮更新电脑源码、App/helpers → 仅本地重建与对账 → 准备同版手机包 → 在获准云端更新窗口发布 App 3 并覆盖升级手机。

仅本地重建时，从本人 ROOT 执行以下命令，PY 为该项目 Python。

```text
PY scripts/app_desktop.py restore-local --project-root ROOT
```

该命令从当前 SQLite 重建本地 App 展示。普通 `refresh --apply` 可能沿已有门禁发布，操作时按实际目的选择。手机解析器也须升级，设备不可用时记录待验收。实际同步仍核对两道门禁和本人的授权范围。

更新器及发行索引必须声明固定源码的实际 snapshotSchema，不再把 App 3 包标为 2。兼容测试使用合成库/缓存和隔离存储，不连接用户真实云端。

发布器会严格校验已认证旧 App 2 的字段、对账和身份，仅用于识别安全可升级的历史槽位/缓存；这种内部核验不会把旧数据补零后交给展示。已存在的旧 pending 必须由新的合法 App 3 输入重新 stage，不能直接上传；revision 接续旧缓存、pending 与已确认发布下限，保留恢复证据。

## 失败后保留什么

保留当前业务账本、有效缓存、原 pending 和发布恢复证据。按生成、校验、发布、手机获取各环节定位。当前月、sourceHash 和实际 coverage 都须匹配才能声明展示最新。开发验证使用合成数据，设备或云端结果按实测另报。
