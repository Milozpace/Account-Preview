# 开发、同步与发布规范

开发必读：[开发状态与交接](开发状态与交接.md) → [版本与分支管理](版本与分支管理.md) → 本文。共享开发统一进入 `dev`，公开与个人按各自版本输入和授权交付。

## 按本次交付选择路径

| 本次任务 | 走哪条路径 | 需要交付给维护者的结果 |
| --- | --- | --- |
| 文档审查与修订 | dev 短期分支，本地验证提交 | 改动说明、实际文档和未解决项，按审阅授权再上传 |
| 共享功能或修复 | 短期分支开发、合成验证、集成 | 固定提交、测试与组件影响 |
| personal 本地交付 | 固定源码与本机个人版本配置 | 本地索引、组件与设备回执 |
| 公开 Release | 固定候选、三平台组件、最终说明 | 最终资产清单、升级验收及针对该版的发布确认 |

以下 PY 为执行工具所需的项目 Python，命令从工具源码根执行，路径和版本占位均由 Agent 核对后替换。

## 一个共享来源，各自独立使用

共享源码统一在 Account-Preview 开发。个人 Account 和朋友项目各自保留 SQLite、原始账单、规则、预算、凭据、身份、配对、同步门禁和偏好；不互相同步业务数据。公共用户消费已发布版本；维护者 personal 使用经校验的本地构建包。Git 提交、CI 候选、个人本地交付与公开 Release 分开记录。

两个构建档案各自从经验证的固定提交生成，可选用相同的共享提交。

| 档案 | 用途 | 应用标识 | 桌面绑定 | 支持平台 |
|---|---|---|---|---|
| preview | 新用户与朋友 | com.account.preview | AccountPreview | Windows x64、Mac arm64、Android arm64 |
| personal | 已部署的原个人版 | com.account.probe | AccountDesktop | Windows x64、Android arm64 |

身份不随产品版本改变。Android 覆盖安装必须沿用对应档案首次安装的签名；私钥不提交、不放 CI Artifact/Release。personal Mac 没有既有部署，本轮不承诺提供。新增身份需要明确设计，不通过重新配对绕过升级。

## 每个开发任务

1. 在 Preview 从 `dev` 切短期功能或修复分支。旧版 hotfix 从对应已发布 tag 或维护线开始。先检查已有修改、来源提交及目标分支，相关测试和说明随代码更新。测试使用合成数据。
2. 验证通过后主动提交本次文件，按已授权范围推送；CI 只验证并产出候选 Artifact，不创建 Release。
3. 报告完成的功能、测试、未验收设备及是否达到发布条件。不得因代码已提交就报告用户 App 已更新。
4. 原个人目录发现的新问题，也回到 Preview 修共享实现；个人数据操作继续只在本人目录进行。旧个人项目中保留的源码是当前部署副本，不再成为第二开发来源。
5. 验证后合回 `dev`，旧版修复回流共享开发线。公开发布线冻结后只纳入交付必需的变更，`main` 跟随实际经验证的公开交付。个人交付分支保留固定提交，后续共享任务从 `dev` 开始。
6. 更新共享开发状态、受影响契约与测试结果，不只写工具专属记忆。草案/实施方案留忽略的 local 供审阅，正式通用规范随实现入库；本机路径和私人状态不进入共享 docs。

## 过渡源码同步

2026-11-01 的历史月份/桌面焦点修复是从个人版向共享源码的一次语义迁入；保留 Preview 原有 Mac、初始化和身份隔离能力。月份起点取各人自己的账本，不固定作者月份。

后续必要的过渡转移使用 `scripts/source_sync.py`。清单是本机 JSON 数组，例如 `["scripts/ledger_snapshot.py", "tests/test_month_history.py"]`，必须逐项明确：

```text
PY scripts/source_sync.py --source 源绝对目录 --target Preview绝对目录 --files 本机清单.json
PY scripts/source_sync.py --source 源绝对目录 --target Preview绝对目录 --files 本机清单.json --apply
```

基线保存在目标 `.runtime/product/source-sync/`。仅源端改变且目标与上次共同内容一致时可更新；目标独有修改保留；双方都改或首次就不同时报冲突。先按语义合并冲突，工具不盲目全文覆盖。没有冲突时整批执行并保留恢复字节；重复不会重复修改源码。中断锁/pending 清单存在时先恢复核对，不删除标记强行继续。

数据、个人说明、凭据、生成目录和构建身份文件不在同步范围；不整库合并原私人 Git 历史。日常共享改动在 Preview 集成，公开用户按 Release 更新，个人使用经验证的本地交付。

## 版本约束与构建

公开版以根目录 `release.json` 为版本输入。先预览拟交付版本及安装序号，核对实际交付和设备安装下限，再由工具同步生成元数据。公开 CI 仅构建 preview 的 Windows x64、macOS arm64 和 Android arm64 组件。

```text
PY scripts/product_version.py check
PY scripts/product_version.py set --version 计划交付版本
PY scripts/product_version.py set --version 计划交付版本 --apply
PY scripts/release.py version-check
```

个人版使用隔离源码工作树，版本与 Android 安装序号从本机 `local/personal-version.json` 读取。采用显式绝对路径，在 Windows、Android 的构建、打包和准备索引时复用同一配置。先用版本工具核对配置、已交付版本和各端安装下限，新的个人交付版本和 Android 安装序号都须递增。示例中的 `COMMIT` 是固定源码的完整 SHA，`PERSONAL_VERSION_FILE` 是个人配置绝对路径。

```text
PY scripts/personal_version.py --file PERSONAL_VERSION_FILE show
PY scripts/build_profile.py --profile personal --platform PLATFORM --personal-version-file PERSONAL_VERSION_FILE --isolated-build --apply
PY scripts/release.py bundle --profile personal --platform PLATFORM --binaries BINARIES --installer INSTALLER --output COMPONENT_ZIP --personal-version-file PERSONAL_VERSION_FILE
PY scripts/release.py prepare --distribution personal-local --directory DELIVERY --commit COMMIT --notes NOTES --personal-version-file PERSONAL_VERSION_FILE
```

选择个人档案后使用原签名构建，在该平台的个人构建工作树打包，`bundle` 以该工作树当前 HEAD 为来源。在同一提交的干净共享工作树准备索引，组件、源码及校验文件均留本机。个人索引含独立版本、`sourceVersion`、commit、原生版本与 Android 安装序号。旧索引与回执按原格式验证，保持原资产和安装保护。安装使用匹配的 `personal-local` 目录，实际设备状态查回执。个人索引声明 `skillPolicy: local-only`：过渡期仍携带公开 Skill 供旧更新器识别，使用根升级到支持该策略的更新器后，可用 `prepare --omit-skill` 生成不含公开 Skill 的源码包。发布 Skill 和个人 Skill 的策略见[开发状态与交接](开发状态与交接.md)。

## 先准备说明初稿，等本人润色或确认

说明固定包含“本次更新”“升级说明”“给 Agent 的更新指引”；无额外衔接时明确写“本版无需额外处理”。有衔接操作时同步追加固定源码中的 `docs/版本衔接指引.md`，保留跨版本尚可能适用的事项。

Agent 根据实际变更与验证结果，参照[模板](../templates/版本发布说明.md)在忽略的 `local/release-notes/版本.md` 起草版本说明，交维护者润色或明确确认最终稿。此约定按维护者 2026-11-03 的纠正执行，不再要求本人从零撰写，也不将初稿当成已批准文案。原稿只用于 Release 正文和哈希核验，不复制到上传目录，不作为附件。准备工具拒绝空说明、模板路径及占位。

1. 先核对 README、入门、手机和更新入口的版本说明仍准确，下载步骤按实际发布索引选择，不能永远固定旧包。完成源码提交，确认工作副本干净；固定完整 commit。若本轮 CI 之后又改了源码/说明，发布准备必须针对最终提交重新取得匹配候选，不能伪造旧产物的来源提交。
2. 取得该提交三个 preview CI 组件 ZIP。Android 沿用 preview 既有离线签名签好，再打入 ZIP；unsigned Artifact 不能分发。组件内清单须标同一 commit。个人包只在本机生成与保存。
3. 候选目录放齐各组件；使用 notes 文件准备对应源码和发布索引，发布前须取得本人对最终文案的确认：

```text
PY scripts/release.py prepare --directory dist/版本候选 --commit 完整提交 --notes local/release-notes/版本.md
```

默认命令仅校验三个公共平台、固定源码及已审阅说明，生成源码 ZIP、`release-manifest.json` 和 `SHA256SUMS`，共六项公开资产。候选准备与远端发布分开执行。目录混入个人包、Markdown 原稿或其他文件即拒绝。发布时只使用准备结果的 assets 白名单（或 release.public_assets 复核结果）。索引仅列 preview，保留 notes 哈希而不附原稿。

4. 向维护者展示具体版本、固定提交、notes 最终稿、最终资产和验收状态，取得针对该版及最终文案的明确确认；已有明确授权不重复询问。
5. 获准后，Agent 才能创建该固定提交的 tag 并上传正式预发布 Release，原样使用已由本人润色或确认的 notes；发布前再次检查说明哈希和产物未变化。不得复用首次试用版的授权作为以后发版的长期许可。

已发布 tag 不移动，安装包、说明与校验值不原地替换；需要修正则另发新版。仅文档修改可以先提交到 main，但不能将新运行时代码搭配旧安装包指导首次安装。

## 文档独立审阅与上传

文档草稿和审查报告先留本机，提供可读取的文件与差异。用户要求先审阅时，本地验证与提交完成后等待对本次文档的明确通过，再推送。README 的本人定稿单独保留，后续改动按实际授权执行。

获准上传时核对 main 与 dev 的差异，只带本次批准内容。文档新增了开发中工具能力的说明时，写清最低工具要求和旧版分支。固定 Release 内的源码包及资产继续保持原发布来源，新增默认分支说明用于引导选择正确的同版操作。

## 公开仓库与发布权限

维护者已于 2026-11-01 将仓库设为公开，读取源码与 Release 可匿名进行，无需邀请或 gh 登录。推送、CI 管理和发布仍使用维护者权限；每版须明确确认发布，说明先由 Agent 起草、本人润色或确认，不把令牌贴进聊天。

`release.json` 和更新清单暂沿用 `channel: private-preview` 这一历史协议值，表示现有试用更新频道，不是仓库访问控制，也不会要求普通用户登录。为了兼容已部署更新器，本轮不改频道名、安装身份或同步协议。

公开后持续执行 `PY scripts/public_readiness.py` 和 `PY scripts/release.py audit`。历史检查包括所有可达提交、历史文件、提交信息及注释标签中的已知敏感模式；已删除文件也不跳过。工具只报告位置，不输出命中内容，不重写历史、不改可见性。扫描通过仍需人工复核图片/作者信息、Issue、Actions 日志和 Artifact、旧 Release、第三方素材及依赖许可。项目正式开源许可证由维护者选择；公开可见不自动等于已授予开源许可，本轮不替本人选许可证。
