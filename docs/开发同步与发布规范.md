# 开发、同步与发布规范

## 一个共享来源，各自独立使用

共享源码统一在 Account-Preview 开发。个人 Account 和朋友项目各自保留 SQLite、原始账单、规则、预算、凭据、身份、配对、同步门禁和偏好；不互相同步业务数据。版本更新只消费已发布版本。Git 提交、CI 验证产物、正式 Release 分开记录。

当前提供两个构建档案，均来自同一提交：

| 档案 | 用途 | 应用标识 | 桌面绑定 | 支持平台 |
|---|---|---|---|---|
| preview | 新用户与朋友 | com.account.preview | AccountPreview | Windows x64、Mac arm64/x64、Android arm64 |
| personal | 已部署的原个人版 | com.account.probe | AccountDesktop | Windows x64、Android arm64 |

身份不随产品版本改变。Android 覆盖安装必须沿用对应档案首次安装的签名；私钥不提交、不放 CI Artifact/Release。personal Mac 没有既有部署，本轮不承诺提供。新增身份需要明确设计，不通过重新配对绕过升级。

## 每个开发任务

1. 在 Preview 的功能分支开发，先检查已有修改，相关测试和说明随代码更新。合成数据作测试，不读个人账本。
2. 验证通过后主动提交本次文件，按已授权范围推送；CI 只验证并产出候选 Artifact，不创建 Release。
3. 报告完成的功能、测试、未验收设备及是否达到发布条件。不得因代码已提交就报告用户 App 已更新。
4. 原个人目录发现的新问题，也回到 Preview 修共享实现；个人数据操作继续只在本人目录进行。旧个人项目中保留的源码是当前部署副本，不再成为第二开发来源。

## 过渡源码同步

2026-11-01 的历史月份/桌面焦点修复是从个人版向共享源码的一次语义迁入；保留 Preview 原有 Mac、初始化和身份隔离能力。月份起点取各人自己的账本，不固定作者月份。

后续必要的过渡转移使用 `scripts/source_sync.py`。清单是本机 JSON 数组，例如 `["scripts/ledger_snapshot.py", "tests/test_month_history.py"]`，必须逐项明确：

```text
PY scripts/source_sync.py --source 源绝对目录 --target Preview绝对目录 --files 本机清单.json
PY scripts/source_sync.py --source 源绝对目录 --target Preview绝对目录 --files 本机清单.json --apply
```

基线保存在目标 `.runtime/product/source-sync/`。仅源端改变且目标与上次共同内容一致时可更新；目标独有修改保留；双方都改或首次就不同时报冲突。先按语义合并冲突，工具不盲目全文覆盖。没有冲突时整批执行并保留恢复字节；重复不会重复修改源码。中断锁/pending 清单存在时先恢复核对，不删除标记强行继续。

数据、个人说明、凭据、生成目录和构建身份文件不在同步范围；不整库合并原私人 Git 历史。日常统一在 Preview 开发后不需要反复使用此工具，用户侧按 Release 更新。

## 版本约束

唯一输入是根目录 `release.json`：产品版本、tag、原生版本、Android buildCode、频道和身份平台表。当前 `0.4.1-preview.1` 是未发布候选，不能以 main 最新提交作为用户可升级版本。

```text
PY scripts/product_version.py check
PY scripts/product_version.py set --version 0.4.2-preview.1
PY scripts/product_version.py set --version 0.4.2-preview.1 --apply
PY scripts/release.py version-check
```

新对外版本必须增加原生安装版本和 Android buildCode；只增加 preview 序号不能替代安装版本递增。构建档案工具仅在隔离构建副本使用，不切换开发目录或已安装 App 的身份。CI 从同一固定提交构建各档案。版本变更和能力变更同步说明；实际发布过的版本永不重写。

## 先准备，等本人写说明和批准

维护者将[模板](../templates/版本发布说明.md)复制到忽略的 `local/release-notes/版本.md`，自己填写。Agent 可报告事实与验证清单，不代写面向用户的版本文案。准备工具拒绝空说明、模板路径及占位。

1. 先核对 README、入门、手机和更新入口的版本说明仍准确，下载步骤按实际发布索引选择，不能永远固定旧包。完成源码提交，确认工作副本干净；固定完整 commit。若本轮 CI 之后又改了源码/说明，发布准备必须针对最终提交重新取得匹配候选，不能伪造旧产物的来源提交。
2. 取得该提交六个对应 CI 组件 ZIP。Android 先由维护者使用各自既有离线签名签好，再打入对应 ZIP；unsigned Artifact 不能作为可安装包。组件内清单须标同一 commit。
3. 候选目录放齐各组件；使用本人 notes 准备对应源码和发布索引：

```text
PY scripts/release.py prepare --directory dist/版本候选 --commit 完整提交 --notes local/release-notes/版本.md
```

命令校验六个平台组合、固定源码及用户说明，生成源码 ZIP、`release-manifest.json` 和 `SHA256SUMS`，**不上传、不建 tag、不发布**。发布索引绑定源码及组件哈希、身份、平台、账本/快照兼容版本和 notes 哈希。

4. 向维护者展示具体版本、固定提交、本人 notes 文件、最终资产和验收状态，等待针对该版的明确确认。
5. 获准后，Agent 才能创建该固定提交的 tag 并上传正式预发布 Release，原样使用本人的 notes；发布前再次检查说明哈希和产物未变化。不得复用首次试用版的授权作为以后发版的长期许可。

已发布 tag 不移动，安装包、说明与校验值不原地替换；需要修正则另发新版。仅文档修改可以先提交到 main，但不能将新运行时代码搭配旧安装包指导首次安装。

## 将来公开

本轮保持私有，公开化须维护者另行确认。读公开 Release 可以匿名进行，私有 Release 使用本人本机 gh 认证；不把令牌贴进聊天。

公开前执行 `PY scripts/public_readiness.py` 和 `PY scripts/release.py audit`。历史检查包括所有可达提交、历史文件、提交信息及注释标签中的已知敏感模式；已删除文件也不跳过。工具只报告位置，不输出命中内容，不重写历史、不改可见性。扫描通过仍需人工复核图片/作者信息、Issue、Actions 日志和 Artifact、旧 Release、第三方素材及依赖许可。项目正式开源许可证由维护者选择；公开可见不自动等于已授予开源许可，本轮不替本人选许可证。
