# 给 Agent 的版本衔接指引

本文件随固定发布源码累计维护。更新入口和程序步骤见[更新与恢复](更新与恢复.md)，按目标已发布版本的同版源码执行。核对起始版本、已完成记录与本次授权，再逐项选择适用事项。

| 适用状态 | 要检查的事项 |
| --- | --- |
| preview.5 自带更新器首次加入 RC | 按下文使用本地已发布目录 |
| 从无 INCOME 的版本升级，或尚无历史复核证据 | 选择期间并复核旧收入分类 |
| 旧 App 2 缓存或旧手机 | 按[快照与月份](快照与月份.md)协调同版组件 |
| 已安装目标版本但流程未完成 | 核对实际记录，只续接未完成事项 |

## preview.5 到 0.4.0-rc.1

preview.5 自带的更新器只自动发现 preview。先取得 rc.1 Release 的完整清单、固定源码与当前 preview 桌面组件，再执行 `check --release-dir 目录`，预检通过后对同一目录执行 update。环境需要准备时使用项目外部解释器与 prepare-python，完整命令见[更新与恢复](更新与恢复.md)。rc.1 支持同系列后续 RC 发现。personal 继续使用获准的 personal-local 目录。

## 每次更新都要做

1. 核对本人 ROOT、安装身份及程序基线，预检后按更新授权覆盖，保留数据、预算、原件、私人规则、配置、凭据、配对和发布门禁。朋友使用 preview，原个人安装沿用 personal；不混装。
2. 更新完成后实际重读 releaseDocs 中的本文件和更新说明。Preview 读取已同步的官方记账 Skill 与所需 references，personal 读取本人维护的入口并核对目标业务契约。处理策略以实际工具支持和发布索引为准。
3. 从旧安装版本到目标版本逐项检查下面累计事项。不能只看最后一版 Release 正文，也不能因已经装过该版本就推断衔接完成。旧版没有指引时明确报告，按新版本适用事项继续。
4. 在本人忽略的 `local/版本衔接记录.md` 留版本／固定提交、事项、所选期间、已完成／暂缓状态及本机审核批次证据；不得记录完整订单或凭据，不提交共享仓库。已有记录须与当前账本／审计证据核对，不只信一个“完成”标记。程序更新器不执行这些业务写入。
5. 程序覆盖、文档读取、账本衔接、快照、云端和设备分别报告。用户授权“按该版指引完成更新”时，在已确定范围内连续完成；只有软件升级授权而未包含改账时，先说明具体纠正范围并取得业务授权。长期历史范围或真实分类歧义仍须询问。

## 0.4.0-preview.5：旧收入分类复核

适用：从不支持 INCOME 的旧版本升级，或未完成本事项的使用者。全新空账本无需改账；已经支持收入且有核验证据完成本事项的，按记录续接，不重复重审全部历史。后续新账按同版日常 Skill 直接审核。

### 选择范围并定向查询

先运行只读查询（PY 为本人项目托管 Python，ROOT 为本人绝对根）：

```text
PY scripts/account.py --root ROOT income-review-candidates --months 3 --limit 50 --offset 0
```

按北京时间当前自然月及前两个月定位；账本实际历史跨度不超过三个月时检查全部已有历史，不因账本很久没更新就漏掉短历史。未来日期不纳入默认复核。返回账本起止月、请求范围、实际查询范围、`historyExceedsWindow`、`matchedRecords`、`nextOffset` 和必要证据。`historyExceedsWindow=true` 时先询问使用者选最近三个月、六个月、其他 N 个月或全部；等待期间可以完成程序更新，但不先提交历史纠正。

```text
PY scripts/account.py --root ROOT income-review-candidates --months 6 --limit 50 --offset 0
PY scripts/account.py --root ROOT income-review-candidates --months all --limit 50 --offset 0
```

`--months` 接受正整数或 `all`，后者明确覆盖全部账本，包括未来日期，未来异常需单独核对；`--limit` 为 1–100，`--offset` 为非负整数。按 `nextOffset` 翻完所选期间的所有候选，先完成只读分页再写入，避免写入后候选减少使 offset 跳过记录。查询无候选也要报告范围，不能推断范围外没有收入。

### Agent 实际审核

查询在数据库端筛选非 INCOME、原始金额非零且原始方向为收入或旧口径为 STRUCTURAL／EXCLUDED 的候选，不依赖关键词命中。候选不是收入结论：结构性支出、退款、互转、报销返还、代收代付、借款及本金划转仍须按真实事件排除；不能只看收支方向或原金额。

结合原始类型／分类、交易说明、状态、现有事件／分类、语义说明及本人确认判断。必要时按返回的具体记录 ID 有限核查原记录、关联或来源；不遍历所有旧原件、不重新导入、不凭同额造关联。明确证据不足的记录保留原状和待确认原因。收入冲回继续遵守同版 Skill 的负原始金额及关联约束，不改原始金额制造冲回。

### 审计纠正与验收

读取本身份适用 Skill 的审核契约，并核对同版[数据字典](数据字典.md)。审核文件使用 `records: []` 和明确 `updates`，沿用现有 ID；将有依据的实际收入改为 `统计口径=INCOME`、`计入消费金额=0.00`、空资金池，填写事件、主分类和说明。每项保留真实理由和确认来源，原始字段、订单、ID、来源、预算和私人规则继续保留。

```text
PY scripts/account.py --root ROOT import --input ROOT/.runtime/本次收入复核.json
PY scripts/account.py --root ROOT import --input ROOT/.runtime/本次收入复核.json --apply
PY scripts/account.py --root ROOT verify
PY scripts/account.py --root ROOT import --input ROOT/.runtime/本次收入复核.json
```

正式工具写前使用 SQLite Backup API，事务提交并记录修改前后值。提交前核对 import 的展示／云端后处理与本人既有授权：配置和原生双门禁不自动改变，升级授权不扩大云端授权；若本次未授权既有自动发布，先解决授权边界再执行，不能先写后问。无纠正项不提交空批次。

核对本次收入笔数、金额，以及消费／四池的实际影响；旧结构性误记导致的汇总纠正须如实说明，不能要求消费数值强行不变。核验原始字段与来源保持、关联／汇总正确，重复预检无新增或修改。重跑候选查询时已改正的 INCOME 不再返回；仍返回的非收入／暂缓项留审核记录，不为清空候选而改账。

同轮升级电脑源码、App、三件 helpers 和所需手机 App。收入使用 Web schema 2／App schema 3，旧手机不能读取新 App 3 快照；按 `快照与月份.md` 的顺序处理本地刷新及获准云端同步，保留旧有效缓存，不补零冒充收入。设备未连接标未执行，更新失败不自动恢复旧业务账本。

桌面绑定缺失时，可在设置中选择本人原账本目录恢复。选择器先核对既有绑定，再从本目录 SQLite 本地重建 App 3 展示；此恢复操作不调用云端发布器，不修改账本业务。其他账本绑定冲突或重建失败时不替换原绑定；后续云端同步仍单独按本人授权执行。

## 后续版本

每版 Release 固定保留“本次更新”“升级说明”“给 Agent 的更新指引”。新衔接事项追加到本文件，写明适用起点、操作、授权边界与验收；无额外事项的版本写“本版无需额外处理”，不删除此前尚可能适用的事项。
