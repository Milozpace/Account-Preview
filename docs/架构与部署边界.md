# 架构与部署边界

开发开始先读[版本与分支管理](版本与分支管理.md)和[开发状态与交接](开发状态与交接.md)。本文说明跨组件修改必须保持的边界。

## 数据流与组件

```text
SQLite（唯一业务来源）
  → ledger_calculation 统一整数分计算
  → Web 快照（浏览器看板）
  → App 快照（共享字段 + App 契约/月份覆盖）
       → desktop_bridge → Rust 校验 → Windows/macOS 桌面界面
       → 原生发布器 → 加密双槽 → Android 校验/缓存/只读界面
```

桌面与浏览器共享展示组件，不代表桌面直接读取 dashboard.json。App 和 ledger_cli、bill_inbox_cli、sync_diagnose 来自同一原生 crate；修改快照解析/共享协议时必须同轮构建、核验和部署对应 helpers。组件回执保留同一完整 commit、profile、版本、平台和哈希，不能拿旧 helper 搭新导出器。

## Python 与工作目录

开发和使用环境均使用各自 ROOT 的项目 `.venv`（Windows `.venv/Scripts/python.exe`，macOS `.venv/bin/python`），由 bootstrap/uv 准备锁定依赖。`.runtime/python` 是基础解释器，不等于安装了 openpyxl 等项目依赖的环境。不能从开发根借解释器对另一个使用根执行 import/refresh。

运行 npm 测试/构建时选择 app 或 dashboard 项目，避免根目录临时依赖缓存混入工作区；生成缓存按忽略规则保留，不为制造干净状态删除用户文件。fixture 用合成数据，保留可读格式。Windows/AppData 的真实用户配置与宿主重定向视图须核对，不靠重建配对或改绑掩盖路径错误。

## 更新受管理范围

程序更新由 `product_update.managed_name` 白名单管理 scripts/app/dashboard 和指定根配置；官方核心记账 Skill 及 references 有单独的基线、冲突与恢复校验。docs、AGENTS、根级所有者说明、PROJECT_MEMORY、个人规则等不作为普通程序文件覆盖活动使用根。通用文档取更新结果 `releaseDocs` 的同版副本，既有所有者确认继续保留。

测试使用根是保留数据和配置的已使用环境，经版本更新或候选部署可能形成混合态；它不是可 reset/clean 的开发 checkout。以受管理内容、组件清单和候选/更新回执判断对齐；不能把 dev 整库覆盖过去，也不覆盖使用者文档。候选部署沿用保护、备份、原子更新及恢复验证，不绕过正式更新器的保护语义。

## 写入与发布分别验收

import 成功和后处理失败可以同时发生。SQLite 写入先备份、事务验证；快照、云端回读、手机回执分别报告。后处理失败保留有效数据与快照，按恢复流程重建，不重导已经成功的交易。

自动展示发布有两道门：publish.json 的配置与原生安全存储的 publishEnabled。同时核对实际 publisher 身份与状态，不因单一 enabled 推断手机一定被更新，也不为测试自动打开门禁。Android 不承担正式快照发布或 SQLite 写入。

## 本机信息和交接

共享 docs 只放可公开架构和通用操作；开发源码根、测试使用根、个人使用根、已安装组件和证据路径放忽略的 `local/开发环境.md`。方案/草案留 local，稳定正式规范随代码提交。缺个人文件不等于缺初始化，工具专属记忆也不替代共享入口。

UI 可以用可用的原生 Computer Use 实际检查；进程启动不是渲染验收。缺少某平台或设备时写未验收，测试通过不冒充实机通过。
